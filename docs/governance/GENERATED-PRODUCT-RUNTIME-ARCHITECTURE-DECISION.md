# Generated Product Runtime Architecture Decision

## 1. Purpose
This document defines the canonical architecture for the Generated Product Runtime. It establishes the missing boundary between the authoring-time Workbench plugins (which generate code) and the execution-time environment where that code runs and connects to external infrastructure.

## 2. Definition of Generated Product Runtime
The Generated Product Runtime is the independently compilable/executable target application that consumes generated source artifacts. It is the final execution environment. It is explicitly NOT a Workbench plugin, SDK core, or Workbench core.

## 3. Plugin vs Runtime Boundary
- **Plugin (`SaaSFoundry.Plugins.Persistence`)**: Responsible strictly for artifact generation, validation, source templates, and SDK integration. It is an authoring-time tool. It MUST NOT contain runtime database execution logic or NuGet dependencies for PostgreSQL.
- **Generated Product Runtime**: Contains the actual compiled implementations and directly references NuGet packages like `Npgsql` and `Dapper.AOT`.

## 4. Target Application
The Target Application is the commercial product that consumes the generated infrastructure artifacts. Currently, the repository lacks a concrete target application template or project file (`*.csproj`). 

## 5. VibeStock Relationship
VibeStock is the first commercial target application for the EngineeringWorkbench. The Workbench acts as the engineering factory, generating infrastructure artifacts. Those artifacts ultimately become part of VibeStock's executable runtime (the Generated Product Runtime). VibeStock source code does not belong inside the Workbench.

## 6. Core Contract Ownership
`SaaSFoundry.EngineeringWorkbench.Core` is the Golden Reference. It contains canonical platform runtime contracts. The Generated Product Runtime MUST reference this Core assembly to consume these contracts. This dependency graph is architecturally sound and requires no modification to the frozen Core.

## 7. `IJobStorageCapability` Ownership
The contract `IJobStorageCapability` is owned by `SaaSFoundry.EngineeringWorkbench.Core`. The concrete implementation source code is owned/generated by `SaaSFoundry.Plugins.Persistence`. The execution owner is the **Generated Product Runtime**, which compiles and executes the generated implementation against PostgreSQL.

## 8. Persistence Generation Boundary
The `Persistence` plugin generates the source code (artifacts) required for the target application to interact with PostgreSQL. It does not execute PostgreSQL operations.

## 9. API Generation Boundary
The `API` plugin remains a generator. It generates the HTTP API Runtime Source which is compiled into the Generated Product Runtime.

## 10. Authentication Generation Boundary
The `Authentication` plugin remains a generator. It generates Authentication Source artifacts for the Generated Product Runtime.

## 11. BackgroundProcessing Generation Boundary
The `BackgroundProcessing` plugin will act as an artifact generator. It emits Background Worker Source artifacts. The BackgroundProcessing generated code will consume `IJobStorageCapability` at runtime.

## 12. Observability Generation Boundary
The `Observability` plugin generates Observability Source artifacts to be consumed by the Generated Product Runtime.

## 13. Dapper.AOT Ownership
Dapper.AOT runtime execution is owned by the **Generated Product Runtime**. The Persistence Plugin only generates the source that references this external package.

## 14. Npgsql Ownership
Npgsql runtime execution is owned by the **Generated Product Runtime**. The target application's project configuration must provide the required external package references.

## 15. External Runtime Dependencies
The Generated Product Runtime owns all external runtime dependencies (Npgsql, Dapper.AOT, ASP.NET Core, etc.).

## 16. Dependency Graph
```
Generated Product Runtime
├── Depends on: SaaSFoundry.EngineeringWorkbench.Core
├── Depends on: Generated Persistence Source
├── Depends on: Generated API Source
├── Depends on: Generated Authentication Source
├── Depends on: Generated BackgroundProcessing Source
├── Depends on: Generated Observability Source
└── Depends on: External Runtime Packages (Npgsql, Dapper.AOT, etc.)
```

## 17. Cell Relationship
While canonical Cell architecture documentation mentions `Core.Cell`, `Ingestor.Cell`, `Bridge.Cell`, and `System.Cell` (e.g., in Observability), the specific mapping of where the generated persistence and background processing runtime artifacts belong among these Cells is not yet defined.

## 18. Target Project Ownership
The ownership of the generated target application's project file (`*.csproj`) is not yet implemented. No target project exists in the repository.

## 19. Certification Implications
Persistence Stage 6 certification remains `NOT YET`. Generator certification may be valid for artifact generation, but Runtime Persistence certification requires an actual generated runtime implementation executing against PostgreSQL, which does not yet exist.

## 20. Explicit Non-Goals
This decision does not implement the Generated Product Runtime, VibeStock, or any PostgreSQL/JobStorage runtime code. It solely resolves the architectural boundary and governance.
## 21. Runtime Materialization Clarification (v1.1.3)

The Generated Product Runtime foundation was previously scaffolded, but full materialization from the Factory into the target Cell directories was not yet implemented. The pipeline requires formal Runtime Materialization to deterministically construct Program.cs and project configuration.
## 22. Code Generation Planning Clarification (v1.1.4)

The Generated Product Runtime materialization is formally driven by a Factory-owned Code Generation Planner, separate from the agent MissionPlanner, orchestrating an implicit runtime registration contribution model.
