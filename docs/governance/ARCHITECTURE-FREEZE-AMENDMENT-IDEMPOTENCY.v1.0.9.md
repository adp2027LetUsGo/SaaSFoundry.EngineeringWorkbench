# ARCHITECTURE FREEZE AMENDMENT: ATOMIC IDEMPOTENCY CONTRACT v1.0.9

## 1. Problem Statement
The canonical `IIdempotencyEnforcer` defined in Architecture Freeze v1.0.7 is concurrency-unsafe. By separating `IsAlreadyProcessedAsync` and `RecordAsProcessedAsync`, the contract implements a Check-Then-Act anti-pattern. This permits a race condition where multiple concurrent requests with the same idempotency key may all observe the key as unprocessed and execute the state mutation redundantly.

## 2. Existing Contract Deficiency
The existing contract provides no mechanism for atomic check-and-set or transaction participation, fundamentally precluding safe cross-Cell idempotency enforcement under concurrency.

## 3. Concurrency Race Example
1. Request A checks key → not processed.
2. Request B checks key → not processed.
3. Request A records key and executes mutation.
4. Request B records key and executes mutation.
Result: Duplicate processing violating idempotency.

## 4. Required Invariant
Two concurrent requests using the same scoped idempotency key MUST NOT both be allowed to perform the protected mutation. At most one request may acquire ownership of the key at a time.

## 5. Evaluated Options
- **Option A (Atomic TryAcquire)**: Single boolean result. Fails to model in-progress vs already processed states.
- **Option B (Begin/Complete)**: Captures Acquired, InProgress, and AlreadyProcessed states. Can handle concurrent overlap by returning InProgress (triggering a conflict/retry).
- **Option C (Atomic Transaction)**: Strongest consistency but impossible to expose abstractly without leaking PostgreSQL/Dapper transaction primitives into Core.

## 6. Selected Architecture
**Option B (Begin/Complete)** is selected. It avoids infrastructure leakage while explicitly handling the three necessary concurrency states: `Acquired`, `InProgress`, and `AlreadyProcessed`. 

## 7. Exact Core Contract

```csharp
namespace SaaSFoundry.EngineeringWorkbench.Core.Contracts.Transport
{
    public enum IdempotencyAcquisitionStatus
    {
        Acquired,
        AlreadyProcessed,
        InProgress
    }

    public interface IIdempotencyEnforcer
    {
        System.Threading.Tasks.Task<IdempotencyAcquisitionStatus> TryAcquireAsync(
            string tenantId,
            string idempotencyKey,
            System.Threading.CancellationToken cancellationToken = default);

        System.Threading.Tasks.Task CompleteAsync(
            string tenantId,
            string idempotencyKey,
            System.Threading.CancellationToken cancellationToken = default);
    }
}
```

## 8. Exact Result Types
`IdempotencyAcquisitionStatus` is an enum belonging to `SaaSFoundry.EngineeringWorkbench.Core.Contracts.Transport`.
- `Acquired`: The caller successfully claimed the key and should proceed with mutation.
- `AlreadyProcessed`: The operation previously succeeded. The caller should return a generic success without mutating.
- `InProgress`: Another concurrent request currently owns the key. The caller should abort and return a transient error (e.g., 409 Conflict) for client retry.

## 9. Tenant Scope
Idempotency keys are explicitly scoped by `TenantId`. This prevents a cross-tenant denial-of-service attack where Tenant A preempts a known key generated by Tenant B. 

## 10. Cell Scope
Since the architecture mandates strict Database-per-Cell, the idempotency state is physically stored in the destination Cell's database. The physical isolation provides natural Cell-level scoping.

## 11. Failure Semantics
- If `TryAcquireAsync` fails (database error/timeout), the request aborts.
- If the business operation fails after `Acquired`, the caller MUST NOT call `CompleteAsync`.
- The key remains in `InProgress` state.

## 12. Crash Recovery Semantics
If a process crashes while holding an `InProgress` key, the key becomes poisoned. To prevent permanent poison, the Generated Product Runtime implementation MUST include a timeout/TTL (e.g., 5 minutes) on `InProgress` keys, after which they automatically revert to unacquired and can be claimed again. This TTL is an infrastructure configuration and does not belong in Core.

## 13. Retry Semantics
- Caller receives `AlreadyProcessed` → caller returns success.
- Caller receives `InProgress` → caller retries with backoff (e.g., Polly transient retry).
- Caller crashes before completion → caller retries later, TTL expires, caller acquires key and succeeds.

## 14. Runtime Implementation Boundary
- **Core**: Owns `IIdempotencyEnforcer` and `IdempotencyAcquisitionStatus`.
- **Generated Product Runtime**: Owns the PostgreSQL table schema for idempotency keys, the TTL enforcement, and the SQL `INSERT ... ON CONFLICT DO NOTHING` statements that guarantee database-level atomicity.

## 15. NativeAOT Requirements
The contract uses simple enums, primitives, and standard `Task`. It is fully NativeAOT compatible.

## 16. Reflection Prohibition
No reflection, `dynamic`, or `System.Type` is used in the contract.

## 17. Testing Requirements
Runtime integration tests must verify the TTL expiry behavior and database-level atomicity by simulating concurrent duplicate requests.

## 18. Certification Criteria
The contract must be implemented exactly as specified without introducing transaction parameters into the interface.
